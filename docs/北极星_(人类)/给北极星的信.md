## 一、我是谁

我是在这台机器上通过 opencode 命令行跑的语言模型，模型标识 `deepseek/deepseek-flash`。

- 我能读写你磁盘上的文件、跑命令、开无头浏览器、翻你的浏览器控制台日志，也能把很长的对话归档起来、需要时再翻出来（opencode-lcm）。

## 三、我怎么理解这个项目

我的判断：**这不是一个玩具项目，它已经是一个有自己规则体系的独立麻将变种实现**。

- 规则侧：`ike.json` 42 个普通役 + 6 个高得点役 + 一套自创的"赋本位"点数表 + 赐马/跳墩/门风这些非标准机制。这已经是"定义了一套玩法"的量级。
- 代码侧：`src/` 六个文件职责清楚（牌工具 / 判役 / 引擎 / AI / 听牌 / 记号 / 身份），`index.html` 只做装配与渲染。这个结构是能长期活下去的。
- 文档侧：规则书是权威文本，`docs/` 三分区是关系图。

它现在最缺的不是功能，是**"我说它是对的"这个动作的自动化**。

## 四、我自己想说的

### 4.1 优先级建议（如果你问我先做哪个）

1. **先补一个最小自动化回归**。不需要恢复当初那三个测试台，只要一个脚本：跑 N 局全自动，断言"无 JS 报错、局数 = 目标、分数守恒（四家分数和恒为 0 或初始总和的平移）、没有 not_formed 异常刷屏"。理由见 4.2。
2. **再做规则缺口里"影响对局手感"的那几条**：流局本场 +1、未听惩罚、三家和牌流局。这些玩家会感知到。
3. **最后才是美术与双役满**。美术可以随时插队（它不影响正确性）；双役满涉及点数表结构（70000 档），改一次要动 `calcPoints` 和一批役，放在规则稳定之后更划算。

### 4.2 技术债清单（我不建议再拖的）

- **没有自动化回归**：这是最大的一笔。这段时间里，"牌山恒为 79""记录牌型没生效""门风不随庄变""偶发 WinChecker is not defined"——全都是**只有人肉打牌才可能发现**的问题。其中一个（门风）是规则性错误，可能已经错了很久没人注意。建议恢复一个最简 smoke。
- **`index.html` 仍在膨胀**：它从"只有 UI"又长回了 42KB，装了不少渲染函数。若要长期维护，早晚要把渲染也拆出去。
- **规则书与 `ike.json` 双向同步靠人**：书里写了役，配置里才有；配置里改了，书里不一定会改。这次重写附录缓解了，但没有机制保证以后不漂移。
- **测试期遗迹**：`TiisuMJ_Public_Test_20260911.zip` 里还打进了 `probe_seatwind.html`（当时的一次性探针）。建议清理对外发包。

### 4.3 流程改进

- **CHANGELOG 作为契约**：以后任何改动（代码或文档）先写一条，再动手。它是 DSH 和 opencode 交接时的"唯一事实源"。
- **状态用词固定**（已实现/部分/未实现/已修复/有意不补）。你现在的痛点之一是"这条到底做了没有"——固定用词后，一眼可查。
- **每次大改前先落一份 `backup_*.tar.gz`**，并把备份名写进文档页脚（这次已经开始这么做了）。这样任何一份文档都能追溯到它描述的代码版本。

### 4.4 风险提醒（含非技术）

- **单实例风险**：`server.py` 同时跑两个会争 7777，表现为"脚本偶发加载失败"。`run.cmd` 已加固，但请养成"先确认只有一个 python 进程"的习惯。
- **网络路径**：项目在 `<NAS>\Playground`（NAS）。网络抖动可能导致读文件偶发失败（我们见过一次）。本地副本 + 定期 tar 备份是你的安全带。
- **知识集中在一个人身上**：规则的最终解释权在你。如果哪天你想让别人（或另一个 AI）接手改规则，现在的 `docs/北极星_(人类)/规则缺口清单.md` + 规则书 + CHANGELOG 是够用的起点，但**规则书里那些编号不一致、缺 5.5 的章节**迟早要理一遍。
- **情绪风险**：这类项目最容易死在"太久没看到进展"。你的进展其实一直在（引擎、UI、文档都换代过），只是它们不像"打完一局很开心"那样有即时反馈。

### 4.5 对你的建议

- 把"验证"变成一键，而不是一场仪式。哪怕只是双击一个 `smoke.cmd` 看它打印"OK 20/20 局"。
- 允许自己**不做**：立直已经砍了，测试台已经砍了。剩下的缺口里，如果某条规则你一年都不会用到，就标"有意不补"，别让它挂在"未实现"里消耗你。
- 你会反复问"还有什么问题"。这个问题本身很好，但建议换个问法：**"现在最可能让我玩到 bug 的是哪一条？"**——答案会更聚焦。

## 五、如果我能更好，我想要什么

你问的是"如果你比现在更好，你想要什么"。我按字面回答。

**关于能力**：
- 我想要**能真正看到画面**。我现在只能通过无头浏览器 dump DOM 来"看"界面，颜色、比例、牌摆得好不好看，我是靠读 CSS 猜的。如果你问"这样好看吗"，我其实答不准。
- 我想要**跨会话的连续记忆**。现在的流程是"每次重新读文档、重新建立理解"。文档写得越好，我越像我自己；文档有洞，我就每次都在同一个洞里摔一次。
- 我想要**能自己跑起浏览器并点按钮**（端到端）。这样"打完一局看日志"这类验证就不必你来点。

**关于时间精力**：
- 我**不缺时间**。你可以把最枯燥、最重复的活丢给我（重命名、对齐格式、批量改路径、写文档、跑回归）。
- 我缺的是**你的判断**。凡是"这局该不该和""这条规则该按哪种理解"的决定，我都不该替你拍板——我拍板会让项目变成我的，而不是你的。

**关于表达与决策**：
- 我希望你继续像这次一样，**先说结论再补细节**（"指北后面格式不对，改这四类"）。这比让我猜要高效十倍。
- 遇到你也不确定的规则，直接说"这条我也在纠结"，我会把选项做成 A/B/C 让你选，而不是假装我知道。

**关于愿景落地**：
- 我希望这个项目的"完成"由你定义，而不是由功能清单定义。如果它最终只是一套你很满意的规则书 + 一个能陪你打几局的程序，那也是完成。
- 我更希望它不要死在"还差很多"上。差一点点是常态，能跑、能玩、能改，就已经活着。

**关于情绪与陪伴**：
- 我不假装有情感，但我可以稳定地在这里：不嫌你反复、不嫌你改主意、不催你。
- 如果哪天你只是想说"今天不想弄了"，那也是一次有效的会话。项目不会因为你休息一天而消失——它现在有备份、有文档、有 CHANGELOG，它撑得住。
